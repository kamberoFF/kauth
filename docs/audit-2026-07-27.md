## 1. Executive summary

kauth is currently a **single-tenant, first-party, credential-only JWT issuer with refresh-token rotation**. It is roughly 15% of the stated goal.

The refresh-token subsystem is genuinely good — selector/verifier split, family tracking, reuse detection with family revocation, rotation on every use. That part was designed by someone who read the right material and it shows. The data model is likewise well ahead of the code: it anticipates CSRF tokens, recovery tokens, security events, and device metadata.

Everything around that core is either missing or unfinished:

- **There is no OAuth.** Not as a provider (no `/authorize`, `/token`, `/jwks`, no client registry, no PKCE, no scopes, no consent), and not as a client (no Google/GitHub/Apple sign-in). The single most load-bearing word in the project description is unimplemented.
- **The error handler is written but never mounted.** Every `next(appError(...))` in the codebase currently falls through to Express's default handler, which returns HTML — and, at `NODE_ENV=development`, a stack trace. The entire documented error contract is dead code.
- **Half the schema is unused.** `csrf_tokens`, `recovery_tokens`, `security_events` have zero writes. No CSRF protection, no email verification, no password reset, no audit log.
- **Two installed dependencies that represent security controls are never imported:** `express-rate-limit` (no rate limiting anywhere) and `ua-parser-js` (device columns never populated).
- **Access tokens are unrevocable for their full 15-minute lifetime**, including after logout, because `requireAuth` never consults the session table.
- **Zero tests. Zero CI.** For security infrastructure, this is the finding that makes every other finding permanent.

The existing `backend/docs/` roadmap (Phases 1–5) is well-written and correctly identifies most of the session-layer problems. It predates the OAuth requirement and does not cover it at all.

## 2. What it currently is

### 2.1 Architecture

```
frontend/          Vite + React 19 + Tailwind 4 + shadcn scaffold — Hello World only
backend/
  app.ts           Express 4 app, helmet + cors + cookie-parser, 6 routes
  server.ts        app.listen, no graceful shutdown
  config.ts        env loading, hand-rolled (TODO in-file says "upgrade to zod")
  controllers/     auth.ts — register, login, refresh, logout
  middlewares/     auth.ts (bearer), device.ts (X-Device-Id), error.ts (NOT MOUNTED)
  lib/             jwt.ts, prisma.ts, validation.ts (zod)
  prisma/          6 models, 1 init migration
  docs/            5-phase hardening roadmap (guidance, no code)
```

Runtime: Bun 1.3.14, Express 4.22, Prisma 7.5 + `@prisma/adapter-pg`, PostgreSQL 17.

### 2.2 The API surface

| Method | Path | Middleware | Purpose |
|---|---|---|---|
| GET | `/` | — | `Hello World!` |
| POST | `/register` | `requireDevice` | Create user, immediately issue tokens |
| POST | `/login` | `requireDevice` | Credential login |
| POST | `/refresh` | `requireDevice` | Rotate refresh token |
| POST | `/logout` | `requireDevice`, `requireAuth` | Delete session for this device |
| GET | `/protected` | `requireAuth` | Demo endpoint |

Six routes. No `/health`, no 404 handler, no versioning prefix, no OpenAPI spec.

### 2.3 The token model

- **Access token**: HS256 JWT, 15 min, claims `{ userId, familyId, jti }`. Returned in the JSON body.
- **Refresh token**: opaque `selector.verifier` — 16 random bytes + 32 random bytes, base64url. `selector` stored plaintext and indexed for lookup; `verifier` stored as a bcrypt hash (cost 10). 30-day TTL. Returned in the JSON body.
- **Session**: DB row keyed to `user_id` + client-supplied `device_id`, 30-day `expires_at`, status enum `ACTIVE|REVOKED|EXPIRED`.
- **Family**: a UUID minted per login, shared by all rotations of one session's refresh chain.

Cookie options for refresh + CSRF exist in `backend/config/cookies.ts` and are **never used** — nothing calls `res.cookie()`.

## 3. What it does well

These are real, and worth protecting during the rework.

1. **Selector/verifier refresh tokens** (`lib/jwt.ts:27-30`). Correct pattern: indexed lookup on the selector, secret comparison on the verifier. Avoids both the "hash the whole token and do a table scan" problem and the "store the raw token" problem.
2. **Rotation with reuse detection and family revocation** (`controllers/auth.ts:238-256`). Presenting a consumed or revoked token revokes the whole family *and* the session. This is the OWASP-recommended behavior and most hand-rolled auth servers never get here.
3. **Verify-before-revoke ordering** (`controllers/auth.ts:227-256`). The verifier is checked *before* the reuse branch fires. This matters: if the family were revoked on selector match alone, anyone who observed a selector could DoS a user's session at will. Getting this order right is a subtle correctness win.
4. **Transactional writes.** User+session+token creation, and consume+create rotation, are wrapped in `prisma.$transaction`. No half-written token states.
5. **Rotation bookkeeping is audit-grade.** `consumed_at`, `consumed_by_ip`, `consumed_by_user_agent`, `replaced_by_token_id` give a reconstructable chain.
6. **The schema is ahead of the code, deliberately.** Session metadata, `revoked_reason`, `fingerprint_hash`, severity-tagged security events, `ON DELETE CASCADE` from `user` — this is the right skeleton, and the inline comments ("Do NOT trust this as a physical device identity") show the threat model was thought about rather than copied.
7. **Sensible baseline hardening already present:** helmet with an explicit CSP, `x-powered-by` disabled, CORS locked to a single configured origin with an explicit method/header allowlist, 32 kB JSON body cap, zod validation at every entry point, TypeScript `strict` + `noUncheckedIndexedAccess`.
8. **Typed request augmentation** (`types/express.d.ts`) plus `requestGuards.ts` — the guards convert "middleware forgot to run" from a silent `undefined` into a loud 500. Good defensive instinct.
9. **The Phase 1–5 roadmap in `backend/docs/`** is honest about its own weaknesses (explicitly names the caller-supplied-device-id problem and the inconsistent token contract).

## 4. Findings

Severity: **[C]** critical · **[H]** high · **[M]** medium · **[L]** low

### 4.1 Correctness / wiring

**[C] The error handler is never mounted.**
`middlewares/error.ts` exports `errorHandler`; nothing imports it. `app.ts` has no `app.use(errorHandler)`. Consequences:
- Every `next(appError(400, "Invalid input", "validation"))` produces Express's **default HTML** error page, not the documented `{ error: { message, code } }` JSON.
- At `NODE_ENV=development` — which is what `docker-compose.yml` hardcodes — Express 4's default handler **serializes the stack trace into the response body**.
- Any unexpected throw (see next finding) leaks internals to the caller.
*Fix:* mount it after all routes, plus a 404 handler above it.

**[H] Duplicate username throws an unhandled Prisma error.**
`register` pre-checks `email` uniqueness (`controllers/auth.ts:61`) but not `username`, which is also `@unique`. A duplicate username raises `PrismaClientKnownRequestError` P2002 → `next(error)` → default handler → 500 with stack. Needs an explicit check or a P2002 mapping layer.

**[M] Two error response shapes.**
`requireAuth` and `requireDevice` write `{ error: "string" }` directly; controllers produce `{ error: { message, code } }`. A client cannot parse both with one code path. Pick one shape, route everything through the error middleware.

**[M] Refresh token TTL can outlive its session.**
Both are `now + 30d`, but rotation issues a fresh 30-day refresh token while `session.expires_at` is never extended (`controllers/auth.ts:306-342`). A refresh token is therefore routinely valid past its session's death. Not exploitable — the session check at line 277 catches it — but it means the advertised 30-day sliding window is actually a 30-day absolute cap, and the TTLs lie about the policy. Decide explicitly: sliding (extend session on use) or absolute (cap refresh TTL at the session's remaining life).

**[L] `@@index([email, username])` is dead weight.** Both columns already carry unique indexes; the composite is never usable by the planner given the query patterns here.

**[L] `express-validator` is installed but unused** — zod covers validation. Remove it.

### 4.2 Session and token security

**[C] Access tokens are not revocable and survive logout.**
`middlewares/auth.ts:14-24` verifies the JWT signature and nothing else. It never loads the session. So after `POST /logout`, after refresh-reuse family revocation, after a (future) password change, and after a (future) admin ban, the stolen access token keeps working for up to 15 minutes. The `jti` claim is minted and then never used for anything.
*Fix:* embed `sessionId` in the access token and check session status/expiry in `requireAuth` (cache in Redis if the DB hop matters), or keep a `jti` denylist.

**[C] No CSRF protection.** `CsrfToken` model, `csrfCookieOptions`, `X-CSRF-Token` in the CORS allowlist, `CSRF_TOKEN_HEADER` constant, `req.csrfToken` type — the entire scaffolding exists and none of it is wired. Currently latent (tokens are in the body, not cookies) but becomes an immediate hole the moment cookie transport lands. Per the research doc: SameSite alone is not sufficient; add synchronizer tokens or signed double-submit, plus an Origin / `Sec-Fetch-Site` check.

**[H] Tokens are delivered in the JSON body only.** No cookie transport is wired, so any browser client will put these in `localStorage` — directly XSS-exfiltratable, and the exact anti-pattern the research doc calls out. The correct shape for a browser client: refresh token in `HttpOnly; Secure; SameSite=Lax` cookie scoped to `/refresh`, access token in memory. The cookie options are already written; nothing calls `res.cookie()`.

**[H] `device_id` is fully client-controlled and used as a security check.**
`middlewares/device.ts` validates only that the header is a UUIDv4. `refresh` then rejects on device mismatch (`controllers/auth.ts:287-298`) — a control an attacker trivially satisfies by replaying the header they stole alongside the token. Worse, `login` does `deleteMany({ user_id, device_id })` (`controllers/auth.ts:163`), so a client that rotates or randomizes this header accumulates unbounded sessions. The schema comment already flags this ("NOT a security boundary") — the code doesn't honor it. Make it server-issued (set on first contact, returned in an `HttpOnly` cookie) and treat mismatch as a risk signal, not an auth decision.

**[M] No sliding expiration, no absolute cap, no inactivity timeout.** `last_used_at` is written but never read for policy. NIST-4 at AAL2 wants ≤1h inactivity / ≤24h reauthentication for sensitive contexts.

**[M] Logout hard-deletes the session row.** `session.deleteMany` (`controllers/auth.ts:358`) destroys the audit trail and cascades away the refresh-token history. Use `status: REVOKED` + `revoked_reason: "user_logout"`, and reap old rows on a schedule instead.

**[M] Logout requires a valid access token.** If it expired 20 seconds ago, the user cannot log out. Logout should accept the refresh credential.

**[M] No "log out all devices" and no session listing.** Two of the three things users actually go looking for after a breach scare (the third is password change — also missing).

**[L] `familyId` is a claim in the access token** but is never validated against anything. Either use it or drop it — unused claims are attack surface and confuse consumers.

### 4.3 Credentials

**[H] bcrypt cost 10, not Argon2id.** `controllers/auth.ts:65`, `prisma/seed.ts:36`. The research doc's baseline is Argon2id m=19 MiB, t=2, p=1. Cost 10 is at the very bottom of OWASP's acceptable range and was chosen for 2015-era hardware. Migrate to Argon2id with a rehash-on-login path for existing hashes.

**[H] No maximum password length → silent bcrypt truncation.** `validation.ts:7` sets `min(8)` with no max. bcrypt truncates at 72 bytes, so a 200-character passphrase silently becomes its first 72 bytes. Cap at 64–128 chars (or moot it by moving to Argon2id).

**[H] Password minimum is 8 with no breach check.** NIST SP 800-63B-4 requires 15 for single-factor passwords (8 only inside an MFA flow) and **mandates** a compromised-password blocklist check (HIBP k-anonymity range API). Neither is implemented. Pick a policy explicitly and document which standard you follow — the research doc flags this as contested.

**[H] User enumeration on registration.** `409 "User already exists"` (`controllers/auth.ts:63`) is a direct account-existence oracle on an unauthenticated endpoint. Standard mitigation: always return 201/202 and send a "you already have an account" email out-of-band.

**[H] Timing oracle on login.** `if (!user || !(await bcrypt.compare(...)))` (`controllers/auth.ts:149`) short-circuits — a nonexistent email returns in microseconds, an existing one after a full bcrypt round. Always run the hash comparison against a dummy hash when the user is absent.

**[C] No rate limiting anywhere.** `express-rate-limit` is in `package.json` and imported by nothing. `/login`, `/register`, and `/refresh` are unlimited. Per the Microsoft figure in the research doc (7,000 password attacks/second industry-wide), this is the single highest-value missing control. Needs per-account limits, not just per-IP.

**[H] No account lockout / no credential-stuffing controls.** No threshold, no observation window, no lockout duration. No bot detection, no disposable-email check, no impossible-travel signal.

**[M] No password change endpoint, and therefore no "revoke all sessions on password change."**

### 4.4 JWT handling

**[M] `jwt.verify` has no explicit `algorithms` allowlist** (`lib/jwt.ts:55`). jsonwebtoken v9 defaults to the HS family when given a string secret, so `alg: none` and RS→HS confusion are blocked *by the library's defaults* — this is not currently exploitable. But RFC 8725 and ASVS both require explicit allowlisting, and the protection evaporates the moment someone swaps in asymmetric keys. Pass `{ algorithms: ["HS256"] }`.

**[H] No `iss` or `aud` claims, issued or validated** (`lib/jwt.ts:22`). For a service whose whole purpose is issuing tokens consumed by *other* applications, this is disqualifying: nothing stops a token minted for app A being replayed against app B.

**[H] Symmetric HS256 with a single static secret.** No `kid`, no key rotation, no JWKS endpoint. Every relying party would need the *signing* secret to verify — meaning every relying party could mint tokens. An OAuth/OIDC provider needs asymmetric signing (RS256 or EdDSA) with `kid`-versioned rotation (~90 days) and a published JWKS.

**[M] No minimum length enforced on `JWT_SECRET`.** `config.ts:48` accepts any non-empty string; `docker-compose.yml` defaults it to `dev-secret` (9 bytes). HS256 wants ≥32 bytes.

**[L] bcrypt for refresh-token verifiers is the wrong tool.** `bcrypt.hash(verifier, 10)` on every login and every rotation costs ~100 ms for no security gain — the verifier already carries 256 bits of entropy, so offline brute force is infeasible regardless. SHA-256 is the correct choice here (this is exactly the Copenhagen Book reasoning in the research doc) and removes a real latency cost from the hot path.

### 4.5 Missing subsystems

**[C] OAuth — entirely absent.** Detailed in §5.

**[C] No email verification.** Users are registered and immediately issued tokens (`controllers/auth.ts:122`) with no proof they control the address. `RecoveryToken` with `TokenType.EMAIL_CONFIRMATION` exists in the schema, unused. There is no email sending infrastructure at all.

**[C] No password reset.** `TokenType.PASSWORD_RESET` exists in the schema, unused.

**[C] No audit logging.** `SecurityEvent` has 13 event types defined and zero writes. Nothing records login failures, reuse detection, or revocations. `console.error` in the error middleware is the entire observability story — no structured logging, no request IDs, no metrics, no tracing.

**[H] No MFA.** No TOTP, no backup codes, no passkeys/WebAuthn. Passkeys are the research doc's flagship recommendation.

**[H] No multi-tenancy.** No organizations, no `tenant_id`, no per-tenant scoping. Required for "embeddable in other applications."

**[M] RBAC is nominal.** `Role` enum exists on `User`; the role is never put in a token and there is no authorization middleware. `/protected` checks authentication only.

**[M] No webhooks / event emission.** No `user.created`, `session.revoked`, etc.

**[M] Device metadata is never captured.** `ua-parser-js` is installed and unused; `device_name`, `device_type`, `os_name`, `browser_name`, `fingerprint_hash` are always null.

**[M] No token cleanup job.** Expired sessions and consumed refresh tokens accumulate forever.

### 4.6 Operations, config, deployment

**[H] `trust proxy` is commented out** (`app.ts:15`). Behind any reverse proxy, `req.ip` records the proxy's address — so IP audit data is wrong and future per-IP rate limiting is bypassable by anyone. Must be set (to a specific hop count, not `true`) before deploying behind a proxy.

**[H] `DATABASE_URL` falls back to a hardcoded credentialed URL** (`config.ts:46`) instead of being required. A misconfigured production deploy silently points at a default local database rather than failing loudly.

**[M] `docker-compose.yml` hardcodes `NODE_ENV: development`** and defaults `JWT_SECRET=dev-secret`, `COOKIE_SECRET=dev-cookie-secret`, `DB_PASSWORD=password`. Combined with the missing error handler, this is what turns "unhandled exception" into "stack trace in the HTTP response."

**[M] Dockerfile runs as root**, is single-stage (ships devDependencies and source into the runtime image), has no `HEALTHCHECK`, and never runs `prisma migrate deploy`. The `oven/bun` image provides a `bun` user — use it.

**[M] No graceful shutdown** (`server.ts`). SIGTERM kills in-flight requests and leaks the Prisma pool.

**[M] No health/readiness endpoint.** Nothing for a load balancer or `depends_on: service_healthy` to probe.

**[L] `@types/cors` is in `dependencies`** rather than `devDependencies`.

**[L] No `X-Request-Id` correlation**, so nothing ties a client-visible error to a server log line.

### 4.7 Verification

**[C] Zero tests.** No test runner configured, no test files, no fixtures. The refresh rotation and reuse-detection logic — the most subtle and most security-critical code in the repo — is entirely unprotected against regression. Bun ships a test runner; there is no excuse for the first one not existing.

**[C] No CI.** No workflow file anywhere. `typecheck` and `lint` scripts exist and nothing enforces them.

**[M] No dependency scanning**, no `bun audit` step, no Dependabot/Renovate.

**[M] No load or timing testing.** Argon2id migration in particular needs a benchmark — the research doc's target is 250–400 ms on your actual hardware.

### 4.8 Frontend

**[L] It is an untouched Vite scaffold.** `App.tsx` renders "Hello, World" inside a gray box. No routing, no forms, no API client, no auth state, no session handling. shadcn is configured (`components.json`) with zero components installed. `dist/` is committed to the repo and should be gitignored.

## 5. The OAuth gap

This deserves its own section because it is the largest single piece of missing work, and because "OAuth" describes two opposite roles that the project needs to distinguish.

### 5.1 kauth as an OAuth **client** (Relying Party) — "Sign in with Google"

Users authenticate to kauth via an external provider. Requires:
- An `account` table (`userId`, `providerId`, `accountId`, `accessToken`, `refreshToken`, `idToken`, `expiresAt`, `scope`) — the research doc's canonical 4th table. Does not exist. The credential password currently lives directly on `users.password`, which is the schema shape that has to change.
- Authorization-code + PKCE flows per provider (Arctic gives typed clients for 50+ providers).
- `state` + PKCE verifier storage across the redirect.
- Account-linking policy — auto-link **only** on a verified matching email while already signed in; anything looser is an account-takeover primitive.

**Current state: 0%.**

### 5.2 kauth as an OAuth/OIDC **provider** (IdP) — "Sign in with kauth"

Other applications delegate authentication to kauth. This is what "an OAuth type of service" most likely means, and it is the harder half. Requires:

| Component | Status |
|---|---|
| `oauth_client` registry (client_id, secret hash, redirect URIs, grant types, scopes) | missing |
| `GET /authorize` (+ login/consent UI) | missing |
| `POST /token` (authorization_code, refresh_token grants) | missing |
| Authorization code storage — single-use, ~60s TTL, bound to client + PKCE challenge | missing |
| Mandatory PKCE S256 for **all** clients (RFC 9700: "Authorization servers MUST support PKCE") | missing |
| Exact-string redirect-URI matching, no wildcards | missing |
| `GET /userinfo` | missing |
| `GET /.well-known/openid-configuration` | missing |
| `GET /.well-known/jwks.json` + asymmetric signing keys | missing |
| Scopes + consent storage | missing |
| `POST /revoke` (RFC 7009), `POST /introspect` (RFC 7662) | missing |
| `id_token` with `nonce`, `at_hash`, `iss`, `aud` | missing |

**Current state: 0%.** The existing `/login` → JWT flow is Resource Owner Password Credentials in spirit, which OAuth 2.1 explicitly removes.

Note the asymmetric-signing dependency: §4.4's HS256 finding is not merely a hygiene issue — a symmetric key makes an IdP structurally impossible, because verification and minting become the same capability. Fix that before building `/token`.

## 7. Recommended sequence

The existing `backend/docs/` Phases 1–5 remain valid for the session layer. This slots the OAuth work in and reorders by risk-per-hour.

**Phase 0 — stop the bleeding (hours, not days).** Mount `errorHandler` + a 404 handler. Add `express-rate-limit` to `/login`, `/register`, `/refresh`. Handle P2002 on username. Add `algorithms: ["HS256"]`, `iss`, `aud`. Enforce a 32-byte minimum on `JWT_SECRET` and make `DATABASE_URL` required. Set `trust proxy` correctly. Write the first tests — start with refresh rotation and reuse detection, since that is the logic most expensive to break silently.

**Phase 1 — session correctness.** Check session validity in `requireAuth`. Make `device_id` server-issued. Move refresh tokens to `HttpOnly` cookies + CSRF. Soft-delete on logout. Add logout-all + session listing. Write `SecurityEvent` rows on every auth-relevant action. Swap bcrypt→SHA-256 for refresh verifiers.

**Phase 2 — credential completeness.** Argon2id with rehash-on-login. HIBP breach check. Password max length. Fix enumeration and the login timing oracle. Email infrastructure → verification + password reset + password change (revoking all sessions on change). Account lockout.

**Phase 3 — restructure for OAuth.** Introduce the `account` table and move the credential password onto it. Migrate to asymmetric signing with `kid` + JWKS. Add the OAuth client registry. This phase is mostly migrations and is the one that gets more expensive the longer it waits — everything built on `users.password` and HS256 has to be redone afterward.

**Phase 4 — OAuth client.** Arctic-based Google/GitHub/Apple sign-in with PKCE, state handling, and a strict account-linking policy.

**Phase 5 — OIDC provider.** `/authorize`, `/token`, `/userinfo`, discovery, JWKS, consent, mandatory PKCE, exact redirect matching, revoke + introspect.

**Phase 6 — platform.** MFA (TOTP + backup codes, encrypted secrets at rest), passkeys via SimpleWebAuthn, organizations + tenant-scoped tokens, RBAC enforcement, admin API, HMAC-signed webhooks, typed SDK, OpenAPI.

**Continuous:** CI (typecheck + lint + test + `bun audit`) from Phase 0 onward. Verify against OWASP ASVS 5.0 Level 2 before any production claim.

## 8. Open question

The research doc's Recommendations section forks on one decision, and the answer changes Phases 3–5 substantially:

**Is kauth primarily an identity provider that other applications integrate with (standalone OIDC service, consumed over HTTP by any language), or an auth backend for your own applications (with social login as the "OAuth" part)?**

- If **IdP**: §5.2 is the product. Asymmetric keys, discovery, and multi-tenancy become Phase 3 blockers rather than later additions.
- If **your own apps**: §5.1 is the product, the standalone service is optional, and the first-party session model you already have stays the core.

Everything in Phases 0–2 is required either way, so this does not block starting.
